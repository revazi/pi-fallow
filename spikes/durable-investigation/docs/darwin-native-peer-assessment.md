# Darwin native peer authentication assessment

Issue [#155](https://github.com/revazi/pi-fallow/issues/155) · documentation assessment, 2026-11-16. **Native peer credentials are required on both ends of each proposed supervisor connection, in addition to mutual capability authentication and the existing ownership gates. Capability-only is not an approved fallback.** This is not an implementation, certification, or authorization to build/install a helper or run a prototype. Failure, mismatch, unsupported version or inability to establish either check means block; retain `hard-death-process-ownership-unproven`. The [supervisor design](darwin-supervisor-design.md) is a proposal, not current recovery behavior.

## Authoritative evidence and exact scope

Sources reviewed 2026-11-16; source releases alone do not establish an exhaustive shipping macOS/SDK matrix. The local macOS 27.0 `getpeereid(3)` manual was also read, without a process or socket experiment.

Socket pathname permissions and private directories reduce exposure but are not peer authentication; protect directory traversal, bind/listen and stale-path handling separately. A native check must operate on the actual connected endpoint used for the authenticated protocol, not a separately opened socket or a caller-supplied PID. Both sides check before accepting protocol authority, and recheck on every new connection. Credential snapshot timing and descriptor passing mean a passing check alone cannot prove who currently controls the other endpoint.

## Candidate architectures, not approvals

1. **Native socket owner/broker:** a small separately distributed native process owns the listening/connecting stream and calls `getpeereid` on the actual endpoint; Node communicates with it over a separately protected, tightly bound channel. Both host and supervisor directions need checks, potentially requiring native endpoints on both sides. Specify descriptor ownership, inherited descriptors, closure, identity binding and failure propagation. A broker's claim forwarded as ordinary JSON without authenticated binding is not kernel peer evidence. A broker compromise or confused-deputy/descriptor-swap invalidates the boundary.
2. **Node-API addon:** native code owns or receives the actual connected socket and performs the call in-process. Node-API ABI stability does not promise access to private `net.Socket` internals; a supported descriptor ownership/transfer and lifetime contract is unresolved. Prevent close/reuse and TOCTOU between check and protocol use; avoid trusting a JS-supplied numeric descriptor as identity. Native code changes the host's attack and distribution surface.

Neither option currently has an approved design, implementation, signed/distributed artifact, install method or support matrix. No private symbols, undocumented internals, implicit compiler/toolchain, downloads, or auto-install are authorized. Native peer checks cannot be outsourced to the analyzer. If the endpoint binding or safe helper lifecycle cannot be established, stop rather than downgrade.

## Threat model and independent gates

The proposed boundary is a trusted same-user synthetic environment, not defense against a malicious process with the same UID, a malicious same-user analyzer, root, debugger, compromised supervisor, or kernel. Another same-UID process may pass the UID check, steal accessible capability material, replace files or hold/pass descriptors. Restrictive socket permissions and peer credentials help reject other UIDs subject to OS policy; challenge-response and a fresh instance/attempt binding address a different substitution/replay problem only while the capability remains secret and the original supervisor is live. Neither makes the other redundant. A matching UID/GID, PID, socket name, MAC, nonce or combination is not sufficient authority by itself.

* **Instance/attempt continuity:** mutually authenticated fresh challenges, original live supervisor state, immutable attempt binding, replay controls and exclusive ledger fencing are separate requirements. A credential snapshot does not identify the original supervisor instance, prove liveness, or recover it after death.
* **Child ownership and result admission:** supervisor direct-child spawn/exit observations, bounded capture and consistent authenticated completion are separate evidence. Peer credentials do not establish that the child is owned, that analyzer output is trustworthy, or that a result is admissible after supervisor death.
* **Atomic signaling:** no supported Darwin race-safe action tied to the exact owned target has been established. PID/start time/unique ID lookup, even when combined with peer authentication, cannot authorize a subsequent `kill`. Never signal a recovered PID or group from metadata.
* **Descendant containment:** process groups, socket credentials and observation of direct-child exit do not prevent escape or prove all descendants terminated. No cleanup guarantee follows. Failure remains blocked; operator intervention may be necessary.

## Upstream and historical evidence

The spike remains pinned to Durable 1.4.0, not upgraded by this assessment. The current publicly accessible upstream [Durable README at `64a15f4`](https://github.com/earendil-works/pi/blob/64a15f4bee63d761d5398bf4126ea63abef0dc98/packages/durable/README.md) was reviewed 2026-11-16: it calls the API experimental, describes checkpointed tasks, restart/resume and phases rerunning from the top, and distinguishes a cancelled wait from cancelling work. These are orchestration contracts, not a native subprocess ownership, authenticated peer, atomic signal, external effect exactly-once, or descendant-containment contract. No such upstream guarantee was identified in the reviewed documentation; absence from that review is not proof it can never exist. Revalidate the actual selected upstream version before any future integration.

The preserved [standalone audit at `35361b1`](https://github.com/revazi/pi-fallow/blob/35361b12c922b8fac6b8cac461bb12f1af7e2d37/spikes/durable-investigation/docs/standalone-supervisor-audit.md) records absent authenticated live authority, a fixture expiry gap and incomplete protocol helpers. Its historical tests are not authority or containment proof. Its capability-only alternative was an unresolved choice then; the current decision requires native credentials. The branch is preserved read-only, not resumed or approved.

## Decision and bounded next requests

**No-go now** for a standalone prototype, helper build/install, signaling experiments, Durable integration and production. This documentation assessment is a go only for continued read-only investigation. No fallback may relax the native peer or ownership gates. #155 remains open.

Request separate owner authorization, in order: (1) a narrowly scoped design/security review establishing target macOS/SDK and Node matrix, exact bilateral socket ownership, check timing, credential policy, helper distribution, lifetime and threat boundary; (2) if that design passes, a specific authorization to build and run a disposable native helper, with toolchain/artifact provenance, permitted synthetic tests, cleanup safety and stop conditions explicitly stated; (3) only after those results and independent review, a separate bounded prototype authorization defining fixture expiry, protocol/lifecycle slice, safe cleanup, ceilings and no PID/group signal fallback. None of these requests authorizes the next step automatically. Exact atomic action and descendant-containment proof, storage/rollback and same-user isolation remain independent blockers; absent a safe mechanism, stop and report no-go instead of repeating repairs.
