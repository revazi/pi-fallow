# Darwin ownership investigation: API evidence

Related to [#155](https://github.com/revazi/pi-fallow/issues/155). This is an investigation, not an implemented authority or a platform certification. See the [proposed protocol and decision](darwin-supervisor-design.md). Sources below are primary documentation or source, not proof of behavior on every shipped macOS. XNU source is pinned to `f6217f891ac0bb64f3d375211650a4c1ff8ca1ea`; its correspondence to a particular shipping OS/SDK has not been established.

## Evidence and limits

| Mechanism | What the cited interface/source establishes | Inference and unresolved questions |
| --- | --- | --- |
| libproc | Apple's [libproc.h](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/libsyscall/wrappers/libproc/libproc.h) declares `proc_pidinfo(pid, flavor, arg, buffer, buffersize)`; [proc_info.h](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/sys/proc_info.h) defines `PROC_PIDTBSDINFO` and `proc_bsdinfo` with `pbi_start_tvsec`/`pbi_start_tvusec`. | A query is a PID-indexed observation, not a retained handle. Start metadata can help detect mismatches but is not established as unique or as an atomic signal authorization. Errors, visibility, precision and PID reuse must be tested for each target release. |
| Process unique identifier | Apple's [proc_info_private.h](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/sys/proc_info_private.h) defines `PROC_PIDUNIQIDENTIFIERINFO` and `proc_uniqidentifierinfo.p_uniqueid`, described there as a 64-bit unique identifier, plus parent identity. | This is a real source-defined interface, not evidence that all Darwin identifiers are inadequate. It is in a **private** header; supported SDK availability, permissions, stability, uniqueness scope across boot and use for race-free action are unproven. No supported public signal-by-unique-ID API is established here. A lookup followed by `kill` remains a check/action race. Do not build a production contract on this private flavor without Apple-supported documentation and security review. |
| kqueue | Apple's [event.h](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/sys/event.h) defines `EVFILT_PROC`, `NOTE_EXIT`, `NOTE_FORK`, `NOTE_EXEC`; it says `NOTE_TRACK`, `NOTE_TRACKERR`, `NOTE_CHILD` are no longer supported as of 10.5. See also [kqueue(2)](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/man/man2/kqueue.2). | Notifications are observation, not containment or an atomic handle for signaling. Registration/fork/exit races, event loss, permissions and the ability to follow descendants require experiments; do not infer complete tree tracking from `NOTE_FORK`. |
| Unix socket peers | XNU [un.h](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/sys/un.h) defines `LOCAL_PEERCRED`, `LOCAL_PEERPID`, `LOCAL_PEEREPID`, `LOCAL_PEERUUID`, `LOCAL_PEEREUUID`, `LOCAL_PEERTOKEN`. | Names alone do not establish deployment availability, entitlement requirements or stable semantics on supported SDKs. Peer credentials are a useful additional kernel observation, not mutual authentication of a particular instance or protection from a same-UID adversary. Validate exact `getsockopt` semantics and failure modes on target releases. |
| Node child and socket APIs | [Node 22 child_process](https://nodejs.org/docs/latest-v22.x/api/child_process.html) documents child events, PID, `kill`, detached children and the reuse risk of signalling an exited child; [Node 22 net](https://nodejs.org/docs/latest-v22.x/api/net.html) documents local sockets. | Live JS `ChildProcess` objects are not durable handles transferable to a replacement host. The documented APIs cited do not provide Darwin `proc_pidinfo`, kqueue proc filters or Unix peer credential access as a supported high-level Node interface. A native helper/addon is needed to investigate those observations; it does not itself solve ownership, IPC bootstrap or containment. Node 22.19+ is the repo engine, not a claim that all Node/macOS combinations work. |
| Process groups | [kill(2)](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/man/man2/kill.2) specifies PID and negative process-group targets. Node documents Unix `detached` as making a child leader of a new process group and session. | A process can escape its group; group IDs can be reused and membership changes. A group signal is neither proof of current ownership nor exhaustive descendant containment. |
| launchd | Apple's [launchd.plist(5)](https://github.com/apple-oss-distributions/launchd/blob/d448a1c8f70a61202f8705f94337f686b87c30c4/man/launchd.plist.5) describes job lifecycle, `KeepAlive` and `AbandonProcessGroup`. | A managed job could outlive a host, but configuration, per-user domain, deployment and restart identity need design. A restarted job is not the original supervisor, and launchd process-group behavior does not establish exact tree containment or authenticate receipts. This investigation proposes no launchd installation. |

## Local facts and scope

On the investigation machine `node --version` reported v24.12.0 and `sw_vers -productVersion` reported 27.0.1. These are environment observations only; no native API or supervisor experiment was run. In the current spike `src/util.ts` spawns detached and signals a group for live abort/overflow, while `src/durable.ts` blocks ambiguous hard-death in-flight reconciliation. Existing artifact reconciliation is a separate spike policy, not evidence of authenticated supervisor output. No tested Darwin version matrix, same-user security boundary, atomic signal primitive, or tree-cleanup guarantee is established.
