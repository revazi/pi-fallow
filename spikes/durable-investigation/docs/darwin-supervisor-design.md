# Darwin supervisor: investigation-only design and decision

Related to [#155](https://github.com/revazi/pi-fallow/issues/155); this does **not** deliver its prototype or security acceptance criteria. The [API evidence](darwin-api-evidence.md) separates source facts from inference. Everything below is a **proposed contract**, not current behavior or a recovery guarantee. The existing spike remains unchanged: in-flight ownership ambiguity blocks, and its artifact reconciliation has its own existing rules. The stronger result-admission rules below must not be attributed to that implementation.

## Threat model and boundaries

The intended experiment has one host/ledger owner, one supervisor instance per attempt, a trusted synthetic analyzer executable, and a local filesystem. The supervisor is the analyzer's direct parent, owns capture pipes and holds its authority in memory across *host* death. It must not pass authority keys or writable receipt/artifact descriptors to the analyzer. The host verifies the ledger and communicates with the supervisor; the analyzer's output is untrusted data, never a receipt. Repository content, output and socket paths are untrusted inputs. The ledger, snapshot, executable, supervisor and owned storage are trusted only within the declared OS-user boundary; permissions and validation reduce accidental and cross-user substitution but do not authenticate files against their owner.

**Same-user attacker limitation:** another process with the same UID may read/modify user-owned state, impersonate a same-UID peer, interfere with processes or access secrets depending on OS policy. A filesystem-stored key, mode 0700, a nonce, peer UID or MAC does not defeat that adversary. A compromised host/supervisor, debugger, privileged user, malicious kernel, and hostile analyzer with the same user's authority are outside the experiment's security claim. If #155 requires protection against a malicious same-user analyzer or peer, this scheme is a **no-go** until a separately reviewed OS isolation and key-protection boundary is specified and proven. Do not treat its MAC as independent provenance under those conditions. Availability attacks, SIGKILL of the supervisor, storage rollback and machine power loss are not prevented.

Trust crossings: host -> supervisor requests must be authenticated and bound to immutable intent; supervisor -> analyzer is direct typed argv with minimal environment, no shell, bounded output and no secrets; analyzer -> supervisor pipes carry data only; supervisor -> host results require authenticated completion and verified bytes; ledger and artifact publication are outside one transaction. Neither executable hashing nor a checked pathname closes replacement between validation and exec; a prototype must explicitly document the residual TOCTOU, not claim secure execution against an adversary who can alter the binary or path.

## Lifecycle and durable state

One active attempt per operation, with random attempt and supervisor instance IDs, never reused. All transitions below are proposed. Crash may occur between any two effects.

| Entity | States and transitions | Authority/failure rule |
| --- | --- | --- |
| Host | admitted -> intent committed -> bootstrap -> connected -> reconciled/blocked | Commit intent before bootstrap. Replacement takes exclusive ledger ownership; absence of a supervisor or acknowledgement never authorizes another launch. |
| Ledger | planned -> launch-uncertain -> running/completed -> evidence committed; any nonterminal -> blocked/cancelled | IDs, request binding and deadline immutable; compare-and-set attempt state, persist cancellation fence before requesting termination. Never reset a deadline on restart. No atomic transaction spans IPC, pipes, files and Durable. |
| Supervisor | bootstrapping -> ready -> child active -> completed -> retired; failure -> unavailable | Per-attempt instance accepts at most one spawn; duplicate identical requests return state, conflicting requests reject. A fresh/restarted supervisor is a different instance, cannot attest to the old child. No post-mortem reconstruction from files alone. |
| Analyzer | not spawned -> running -> exited/unknown | Spawn exactly once by the supervisor, direct child observation only. On supervisor death child status and descendants are unknown, not proven gone. |
| Receipt | absent -> authenticated active/completed response -> consumed/expired | In-memory supervisor state is authoritative in this experiment; a persisted copy is a locator/diagnostic only. A live authenticated supervisor must reaffirm it. No supervisor means block, including apparently complete files. |
| Artifact | capture -> sealed bytes + digest -> staged -> published -> ledger referenced | Supervisor bounds capture, seals and serves exact bytes; host rehashes and validates before publication, then commits evidence idempotently. A staged/published file without authenticated live completion is not sufficient in this proposal. Partial files, late data and conflicts are quarantined, not clean results. |

A host dying after intent but before establishing authority leaves uncertain launch and blocks. A host dying after completion but before evidence commit may ask the *same live instance* for the same completion and bytes. Evidence commit is conditional on the still-current ledger version and cancellation fence. An already committed matching evidence record is returned idempotently; a different digest or attempt is a conflict. A crash after evidence commit but before acknowledgement must not re-execute. These are proposed rules, not tested behavior.

## Local IPC v1 proposal

This is a protocol sketch with concrete bounds for a **controlled** experiment, not an approved wire specification. A fresh 256-bit random capability key and 128-bit random instance ID are created by the host per attempt. Bootstrap only via a private inherited pipe/socketpair to the directly spawned supervisor; close unused ends and prevent inheritance by the analyzer. The parent commits the attempt/instance and binding before sending a launch authorization. Store the key in a private owned ledger record for host-restart recovery, never in argv, environment, socket name, logs, analyzer or receipt. Thus its confidentiality/integrity depends on the trusted-user/storage assumption above; a crash before durable key/intent commit blocks. Key lifecycle, filesystem durability and rollback resistance require review. Supervisor keeps the key in memory; after supervisor death a stored key alone grants no recovery authority.

A per-instance Unix socket lives under a private owned directory, with a random name, restrictive permissions, no symlink traversal and no untrusted directory components. A stale pathname is never unlinked or trusted merely because a PID seems absent. Before use, open/validate directories and socket type/ownership; peer UID/PID/audit-token checks, if supported, are supplementary, not the root of authentication. Mutual challenge-response proves possession of the capability and ties the live connection to the saved instance ID. A substituted socket without the key fails; a same-user key thief is outside the guarantee. If bootstrap, peer checks, or mutual authentication cannot be established, block; never downgrade to path, PID or unauthenticated IPC.

* Frame: 4-byte unsigned big-endian length, max 64 KiB payload; reject zero, oversized, truncated, invalid UTF-8, duplicate fields, unknown fields/types and unsupported versions. Canonical encoding must be specified independently and tested with fixed vectors before any implementation (for example, canonical CBOR with a fixed schema); never MAC ambiguous JSON serialization. Limit connections (e.g. 2), requests (e.g. 32 per connection), aggregate captured stdout/stderr (64 KiB each), artifact bytes (64 KiB), and time spent on handshake/read/write. No unbounded allocation or storage. Exact limits are prototype choices, not compatibility commitments.
* MAC: HMAC-SHA-256 with domain separation by protocol, direction and message type; authenticate version, instance ID, attempt ID, connection challenges, monotonically increasing per-connection sequence, request ID, payload and result. Both sides use independent fresh 256-bit challenges and verify before processing; reject replayed sequence, duplicate request IDs with differing bodies, unknown message types, wrong instance or wrong binding. Reconnect uses fresh challenges; persist idempotency state in the living supervisor, not only on a connection. Constant-time tag comparison. Key rotation occurs only with a new attempt/instance; never silently upgrade or reuse it.
* Immutable binding `B`: investigation/operation/attempt IDs, supervisor instance ID, 256-bit attempt nonce, snapshot digest and identity, executable resolved path and SHA-256 and declared version, policy/schema IDs and digest, exact typed argv canonical digest, minimal environment/cwd identity, absolute deadline and output bounds. The host and supervisor independently validate equality with the committed intent. This is an identity assertion, not proof execution matched it in the face of TOCTOU. Record protocol/encoding/hash algorithms explicitly; reject unsupported values.
* Messages: authenticated `HELLO`/challenge, `START(B)`, `STATUS(B)`, `CANCEL(B, cancel-id)`, `COMPLETE(B, child-ref, lifecycle-revision, completion-id, direct-child exit-code-or-signal, timestamps, stdout/stderr lengths and digests, truncation/overflow flags, output schema, artifact length/digest)` and bounded `READ(completion-id, offset, length)` responses. `START` and `STATUS` return the authenticated direct-child lifecycle snapshot specified below; `COMPLETE` binds the same child and final observation. Server never accepts arbitrary command, path, PID, signal or replacement binding. A completion is immutable; output is returned over the authenticated channel or transferred through a separately verified descriptor, never accepted from an analyzer-written receipt path. Exact deadline clock semantics, offset/chunk total accounting, canonical schema and storage format remain prototype gates.
* Persistence/version policy: cap ledger and retained receipt records per attempt, bound retention and retire keys upon finalization; do not log keys or raw output. Unknown versions, corrupt/truncated records, stale instance, invalid MAC, incomplete bytes, expired deadline or changed binding block. Migration of nonterminal authority records is forbidden absent an explicit reviewed migration; unknown records remain blocked and operator-visible. No automatic replay, rekey or adoption of a new supervisor after restart.

### Direct-child identity and lifecycle evidence

The supervisor allocates a random 128-bit `child-ref` at instance initialization for its one possible spawn, bound to `B` and its instance before any lifecycle response. It is a protocol correlation identifier, **not** an OS identity or signal capability. An authenticated `START` response and every `STATUS` response include `B`, `child-ref`, a monotonic per-instance `lifecycle-revision`, and exactly one state: `not-started`, `spawning`, `running`, `exited`, or `spawn-failed`. An identical repeated `START` returns the current snapshot and never invokes a second spawn. `spawning` means the outcome is not yet established; a disconnect, missing response or supervisor death at that point is launch-uncertain, not permission to retry elsewhere.

For `running` and `exited`, the snapshot includes the positive PID returned by the supervisor's direct spawn operation, the supervisor's observed spawn time with explicit clock kind, and tagged optional observations: Darwin start time and process unique identifier, each either `present` with value and source/flavor or `unavailable` with a reason category. The prototype must define their widths, clock semantics, acquisition window and failure categories; a later query cannot retroactively prove it observed the original process. Freeze these observations, including unavailable tags, before the first `running` or `exited` snapshot; do not replace unavailable data with a later PID query. These are supervisor-reported observations, not independently authenticated kernel assertions. `spawn-failed` reports a bounded error category and no child PID; ambiguous spawn outcomes stay blocked rather than being represented as a proven failure. No raw OS errors enter the protocol.

The supervisor records transitions from its own direct-child spawn and exit observation, not from analyzer-written files. For an observed exit, `exited` carries the same `child-ref` and PID, an exit code **or** terminating signal, and observation time; an unknown or contradictory outcome blocks completion. A `COMPLETE` requires that exit observation and the separate end-of-capture/sealing conditions, and repeats its `child-ref`, final lifecycle revision and exit outcome. A direct child exit does not establish that its descendants exited or that inherited output pipes closed. If capture does not end within the bounded policy, report incomplete/blocked rather than manufacture a completion. `spawn-failed` is terminal but is not a clean analyzer result.

Revisions increase on recorded transitions and snapshots are consistent: `not-started` -> `spawning` -> `running` -> `exited`, or `spawning` -> `spawn-failed` only for a definitively failed spawn. Rapid exit must still be recorded as spawn then exit; a host may observe only the later snapshot. The same revision must never describe different data; identity fields and exit outcome cannot change once recorded. A reconnecting host compares the live snapshot and `COMPLETE` against any committed observations; mismatched child reference, PID, revision history or exit outcome blocks admission. A later revision may skip intermediate states but cannot regress. State is retained only by the live original supervisor; persisted observations alone cannot reconstruct authority. An authenticated supervisor asserts this evidence within the trusted-user boundary; matching PID, start time, unique ID, `child-ref`, or even a valid lifecycle transcript does **not** authorize signalling, prove race-free ownership, or prove tree containment.

## Authorization conditions

**Signal:** A replacement host never signals a PID or process group from a ledger, receipt, `proc_pidinfo` query, kqueue event or socket filename. It may send an authenticated cancel request only when it exclusively owns the ledger, the attempt/instance/binding match, the live supervisor proves its capability, cancellation is durably fenced and the request is within policy. The supervisor may perform a signal only if the implementation has an independently reviewed, race-safe authority for the exact target and can demonstrate it cannot affect unrelated processes; fresh PID/start/unique-ID checks and a group ID alone are insufficient. No such Darwin action primitive has been established here. If the condition is not demonstrated, do not signal, report blocked/cleanup-unproven and require operator intervention. Timeout or overflow does not waive this rule. A group kill is not authorized solely because the supervisor originally created the group. Exact cleanup of escaped descendants is not claimed.

**Result admission:** Require exclusive current ledger ownership, matching immutable `B`, no committed cancellation, unexpired absolute deadline, supported protocol/schema, authenticated live original instance, consistent direct-child lifecycle evidence and immutable valid completion, allowed exit status, no overflow/truncation, exact bounded bytes and digest matching completion, artifact parsing and policy validation, snapshot and executable checks per admission policy, and an atomic ledger compare-and-set from the expected attempt to evidence. Recheck fences at commit. Any failure blocks and admits no new evidence; a timeout/cancelled result is never clean. Revalidation detects some drift but cannot prove bytes executed or snapshot stayed unchanged throughout execution. In particular, hashes, version strings, and the supervisor's assertions do not turn a malicious analyzer into a trusted one. Committed matching evidence may be read idempotently under the existing ledger policy, not re-created from a stale receipt.

## Failure matrix

| Event | Proposed response | What remains unknown |
| --- | --- | --- |
| Host SIGKILL, live original supervisor | Reacquire ledger ownership, authenticate same instance and binding; query active/completed; do not duplicate launch. Only admit result under all conditions above. | Survival and reconnect are not yet demonstrated. Signal authorization remains separate. |
| Supervisor dies, host alive or dead | Block; no adoption, no PID/group signal, no receipt-only admission. | Child/descendants may remain; operator repair required. |
| Reboot, power loss, clock discontinuity | Block nonterminal attempt; no reboot recovery. Reject ambiguous/lost deadlines and ledger state; no new timeout budget. | Persistence ordering and wall/monotonic clock mapping need design; no power-loss guarantee. |
| Stale/replaced socket, peer mismatch, unavailable IPC | Fail authentication/peer policy and block; do not unlink based on PID or reconnect to a replacement instance. | Same-UID key theft or OS compromise is outside boundary. |
| PID/group reuse, PID/start/unique ID mismatch | Never signal from identity observation; block. Even a match does not authorize signal. | Atomic authorized targeting is unresolved. |
| Ledger/receipt/key tampering, replay or rollback | Reject malformed or mismatched/MAC-invalid data and replay; block. | Same-user key theft and coherent rollback cannot be reliably detected with local state alone. |
| Executable/snapshot/argv/policy drift | Reject mismatched binding/revalidation and block; never launch a substitute. | Check/exec and snapshot mutation races remain. |
| Output substitution, partial/oversize output | Authenticate completion, retrieve bounded bytes, verify digest/shape and cancellation fence; otherwise block. | Authentic malicious analyzer output is still untrusted; cross-user assumptions apply. |
| Forked or escaped descendant | No claim that events or groups enumerate or contain it; do not target unknown processes. Block cleanup-dependent success. | No exhaustive tree cleanup or unrelated-process safety proved. |
| Unsupported OS/Node/native helper, version mismatch, bad storage | Fail closed, keep current conservative path; no auto-install, no protocol downgrade. | Availability depends on future supported matrix. |

## Decision and next gates

1. **Design: conditional go** for this explicitly scoped investigation, subject to independent review of references, threat assumptions and unresolved protocol details; not approval of a security boundary.
2. **Standalone controlled prototype: conditional go** only as a disposable, synthetic experiment under a trusted same-user environment, with explicit operator approval, no Durable integration or production analyzer. It must not signal by unproven PID/group authority. Its primary purpose is to discover whether a stronger supported mechanism exists, not to ship recovery. If no safe signal/containment primitive can be established, stop and report no-go for cleanup rather than weakening the condition.
3. **Durable integration: no-go** until the standalone tests, supported-platform API review, exact action and descendant-containment proof, key protection/trust decision, crash consistency and independent security review satisfy #155. Maintain current blocking behavior until then.
4. **Production: no-go** additionally requires supported Node/macOS matrix and native-helper distribution/maintenance policy, sandbox and executable/snapshot safety, migration, operability, security review and actual production acceptance. Neither this document nor a successful controlled test is production wire certification.

A bounded proposed experiment would use synthetic short-lived executables and temporary private directories only; test real host SIGKILL during active child and after completion, authenticated reconnect/idempotence, no duplicate spawn, rapid exit and spawn failure, missing or contradictory child identity/exit/revision evidence, inherited pipes left open, cancellation/late-result fencing, supervisor death, malformed/oversized/replayed frames, socket/key/receipt substitution, PID reuse, executable/snapshot drift, output substitution, and intentionally escaping descendants. Use unrelated sentinel processes and verify no unauthorized signal; only use a demonstrably safe cleanup mechanism for fixtures and stop the experiment if cleanup cannot be guaranteed. Test hard-death windows around every persistence and publication boundary. Record actual OS/SDK/Node versions and failures. Demonstrate exact owned-tree cleanup under host SIGKILL **only if** a mechanism capable of proving it is identified; negative escape tests alone do not prove it. No prototype has been implemented or run.

Open questions: Is there an Apple-supported atomic process action tied to stable identity, not merely a query? Can a supported isolation/containment mechanism prevent or enumerate descendant escape and protect unrelated processes through exit/reuse races? Can the analyzer be isolated from key/storage access without introducing a privileged or unsupported boundary? What are documented peer credential semantics on each target OS? How are executable/snapshot TOCTOU and rollback addressed? What precise lifecycle, timeout clock, operator repair, launchd deployment and resource limits are acceptable? If these cannot be resolved, the safe decision remains blocked, not a claim of cleanup.
